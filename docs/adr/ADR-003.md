# ADR-003: Public rendering

- **Status:** Accepted
- **Date:** SDD v3.0

## Context

Public pages are the product's value proposition and must meet the SEO,
time-to-first-byte, accessibility, and caching requirements in §§16 and 21.
The CMS has a separate interaction model and can benefit from a richer client
application. Introducing another server-rendering runtime would multiply
deployment and observability concerns before the platform has feature scale.

## Decision

Render public pages on the server using Django templates and theme packs.
React, when introduced, is restricted to the authenticated CMS experience.
Public selectors resolve the portfolio, publication state, locale, and theme,
then render HTML with explicit cache headers and surrogate keys. Themes are
authored as Django templates and remain subject to output-safety checks.

## Alternatives considered

- **Node SSR with Remix/Next:** rejected because it adds a second runtime and
  duplicates routing, deployment, and monitoring.
- **Client-rendered SPA plus prerender service:** rejected because it adds
  complexity, weakens first response performance, and complicates crawlers.
- **Static export only:** rejected because leads, publication changes, and
  custom domains require dynamic request handling.

## Consequences

The public renderer has one application runtime, predictable cache behavior,
and a direct path to server-rendered accessible HTML. Frontend engineers must
work within Django template boundaries for public themes, and the system must
maintain template safety and query-count budgets. CMS UI tooling can still use
React without changing the public delivery architecture.
