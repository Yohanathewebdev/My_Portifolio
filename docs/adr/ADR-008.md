# ADR-008: PostgreSQL row-level security

- **Status:** Accepted
- **Date:** SDD v3.0

## Context

Application-layer portfolio scoping is the primary tenant guardrail, but
leads, uploaded media, and CV snapshots contain the highest-value cross-tenant
data. Section 24.2 explicitly treats an ORM bug as a remaining risk and
requires PostgreSQL RLS as defence in depth. The database must therefore
enforce the current portfolio context independently of selectors and
viewsets.

## Decision

Enable PostgreSQL Row-Level Security on `leads`, `media_asset`, and
`cv_snapshot`. Policies use the transaction's current portfolio/account
context, which application request middleware and worker tasks set before
access. Migrations own policy creation and tests exercise both permitted and
cross-tenant access. ORM scoping remains mandatory even where RLS applies.

## Alternatives considered

- **Application checks only:** rejected because a missed filter or unsafe
  manager could expose another tenant's records.
- **Separate database/schema per portfolio:** rejected because connection,
  migration, and operational costs grow with tenant count.
- **RLS on every table immediately:** rejected for Phase 1 because it adds
  complexity where the data has no high-value cross-tenant exposure yet.

## Consequences

Connection context, transaction boundaries, worker propagation, migrations,
and local fixtures require careful setup. RLS gives a second independent
barrier for the most sensitive tables and limits the impact of future ORM
regressions. PostgreSQL is a product requirement, not an optional development
database.
