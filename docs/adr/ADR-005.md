# ADR-005: Immutable CV snapshots

- **Status:** Accepted
- **Date:** SDD v3.0

## Context

CV configuration is intentionally assembled from current portfolio data, but a
delivered PDF must remain reproducible after the owner edits a job, changes a
theme, or deletes an asset. Section 13 resolves the earlier contradiction
between live configuration and export reproducibility by separating source data
from the artifact's historical input.

## Decision

Every export reads live career and portfolio data, then writes an immutable
`CVSnapshot` containing the resolved content and the template version used.
The PDF renderer consumes that snapshot asynchronously and stores the output
with status, checksum, and render metadata. A snapshot cannot be edited in
place; a new export creates a new snapshot.

## Alternatives considered

- **Always-live rendering:** rejected because a sent or downloaded PDF could
  silently change when source data or templates change.
- **Duplicate editable CV data:** rejected because it creates conflicting
  sources of truth and makes ordinary profile edits expensive.
- **Store only the final PDF:** rejected because re-rendering, diagnostics,
  and integrity checks need the exact structured input.

## Consequences

Storage grows with exports and retention policy must be explicit. The system
gains deterministic auditability: an owner can identify the source snapshot,
template version, checksum, and render status for every delivered artifact.
Template changes affect future exports without reflowing historical documents.
