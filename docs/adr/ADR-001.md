# ADR-001: Account-to-portfolio ownership

- **Status:** Accepted
- **Date:** SDD v3.0

## Context

The v2.0 design mixed a `User 1:1 Portfolio` ERD with requirements for team
accounts and multiple professional sites. The platform boundary must support
billing and quotas independently from the content/isolation boundary. Section
6 therefore distinguishes the account that owns subscription state from each
portfolio that owns public content. A user may also participate in multiple
accounts with different roles.

## Decision

An `Account` owns subscription, quota, and membership state. It has many
`Portfolio` records. Users join accounts through `AccountMembership`, which
stores the role (`owner`, `admin`, `editor`, or `viewer`). Each portfolio keeps
its foreign key to `Account` and remains the tenant boundary for content
models. Signup still creates one user, account, owner membership, and portfolio.
Authorization follows the declarative role matrix in §6.2.

## Alternatives considered

- **User-to-portfolio one-to-one:** rejected because it blocks multiple public
  sites and requires a breaking migration to add teams.
- **Portfolio as the billing boundary:** rejected because quotas and shared
  billing would be duplicated across portfolios.
- **Implicit membership from ownership:** rejected because it cannot represent
  editors, viewers, invitations, or account-level billing administrators.

## Consequences

The initial schema contains one additional join model and membership queries
must be authorized consistently. The model supports multi-site professionals,
teams, account-level entitlements, and future role expansion without changing
portfolio content ownership. Launch UI may expose only the owner role while the
schema and permission layer reserve the other roles for the `team_members`
entitlement.
