# ADR-004: Typed career models

- **Status:** Accepted
- **Date:** SDD v3.0

## Context

The platform serves multiple professions, but career data still has semantics
that generic content blocks cannot express. CV rendering, structured data,
timeline presentation, validation, and future import workflows need stable
field names and relationships. Section 8 deliberately makes profession
suggestions advisory rather than restrictive, so flexibility must not come
from discarding the data model.

## Decision

Implement career history as typed models in the `career` app. Employment,
education, certifications, publications, awards, and related records have
explicit fields, ordering, visibility, and portfolio ownership. Presentation
layers may compose these records into sections, themes, and CV configurations,
but they do not replace their typed source data with arbitrary JSON.

## Alternatives considered

- **Free-form content sections:** rejected because validation, structured-data
  generation, and reliable CV import become application-specific parsing.
- **One generic career JSON document:** rejected because migrations and
  per-record permissions would be opaque.
- **Profession-specific schemas only:** rejected because it would prevent a
  multi-professional account from combining broadly useful career records.

## Consequences

There are more models, migrations, forms, and serializers to maintain. In
return, the system can generate consistent CVs, JSON-LD, imports, filters, and
future analytics. Profession templates may suggest fields or ordering but
must not prevent a professional from using records outside the suggestion.
