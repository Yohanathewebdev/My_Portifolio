# ADR-009: Primary key policy

- **Status:** Accepted
- **Date:** SDD v3.0

## Context

The platform exposes identifiers in APIs, public URLs, audit records, and
asynchronous jobs. Predictable integer identifiers are unnecessarily
enumerable, while high-volume append-only event tables benefit from locality
and compact indexes. Section 26 requires one explicit rule rather than
repeating “UUID where appropriate” judgement for every model.

## Decision

Use UUIDv4 primary keys for all domain models. Use `BigAutoField` only for
high-volume append-only tables such as `AuditLog`, `PageViewEvent`, and
`EmailMessage`, where insertion locality and index size materially matter.
Foreign keys follow the target model's identifier type. The Phase 0 audit log
is standalone until concrete account and portfolio models exist.

## Alternatives considered

- **Integer keys everywhere:** rejected because publicly exposed IDs are
  enumerable and the rule does not address distributed creation well.
- **UUID for every table:** rejected for append-only event volume where
  sequential keys are operationally advantageous.
- **Per-model discretionary choice:** rejected because it creates inconsistent
  migrations and API assumptions.

## Consequences

UUID indexes and foreign keys are larger, and fixtures must generate IDs
explicitly when useful. The policy is predictable, safe to expose, compatible
with distributed workers, and avoids a later migration from integers to
UUIDs. Append-only exceptions remain narrow and documented.
