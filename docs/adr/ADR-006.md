# ADR-006: Payment provider abstraction

- **Status:** Accepted
- **Date:** SDD v3.0

## Context

Billing is required for entitlements but the final provider is a deployment
dependency (DEP-1), not a prerequisite for tenancy and content phases. A
provider's checkout, webhook, customer, subscription, and refund vocabulary
must not leak into account or entitlement services. The platform also needs
idempotent webhook handling and a provider migration path.

## Decision

Define a small `PaymentProvider` interface for checkout, customer and
subscription operations, and webhook verification/normalization. Provider
adapters translate the external API into internal billing events. The
concrete provider is selected by configuration after DEP-1 is resolved.
Billing events retain provider identifiers for idempotency and reconciliation.

## Alternatives considered

- **Direct Stripe coupling:** rejected because it makes the provider decision
  block phases 1–3 and spreads external types through the domain.
- **A generic payment database without an adapter:** rejected because it still
  leaves transport, signature, and error semantics coupled to each caller.
- **Build every provider upfront:** rejected because it adds cost without a
  launch requirement.

## Consequences

The adapter is an additional layer and must be contract-tested against fake
providers and provider fixtures. Domain services remain provider-neutral,
provider replacement is contained, and the team can implement the selected
integration without redesigning account or entitlement models.
